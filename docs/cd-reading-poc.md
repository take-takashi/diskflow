# CD読み取りの実機検証

## 結果

2026-10-20、macOSのCD専用ioctlをPython標準ライブラリから呼び出し、
13曲の音楽CDを単一の音声イメージとして取得できた。
全体を2回読み取って全バイトが一致し、保存ファイルのSHA-256も一致した。
追加のHomebrewパッケージ、FFmpeg、cdrdaoは使用していない。

この結果が示すのは、この環境でCDDA user dataを取得できたことと、反復読み取りの一致。
ドライブキャッシュの影響や、CD側の読み取り誤りまで排除できたとは判断しない。
`archival_verified`は`false`のままとする。

## 環境とCD構造

| 項目 | 値 |
| --- | --- |
| macOS | 27.0.1 / arm64 |
| ドライブ | USB接続 PIONEER BD-RW BDR-TD05 / Rev 1.01 |
| デバイス | 検証時は`/dev/rdisk8`。再接続時は番号を再確認する |
| Python / uv | mise管理の3.14.5 / 0.13.1 |
| セッション / トラック | 1 / 13、すべてオーディオ |
| `.TOC.plist` | 存在し、`plistlib`で取得できた |
| full TOC | format 0x02、180バイト |
| 最初のINDEX 01 | LBA 0 |
| リードアウト | LBA 265649 |
| 保存範囲 | LBA 0〜265648、各2352バイト |
| 音声サイズ | 624,806,448バイト、約625 MB |

`.TOC.plist`の`Start Block = 150`はLBA 0、`Leadout Block = 265799`はLBA 265649。
plist・IORegistry・CD専用ioctlから取得したfull TOCの一致も確認した。

## TOC取得の修正

最初のprobeは音声の読み取り前に、`DKIOCCDREADTOC`で`EIO`になった。
デバイスを開く権限の問題ではなかった。

同じTOC取得で要求バッファ長を変えたところ、65,535バイトは失敗し、
65,534バイト、4,096バイト、180バイトでは成功した。
`formatAsTime = 0/1`はいずれも成功した。
これはmacOS・ドライブ・USB接続を含む今回の環境での観測であり、
ドライブ単体が原因とまでは特定していない。

`src/diskflow/darwin.py`の要求バッファ長を65,534バイトへ変更し、
モックテストにもその値の確認を追加した。

## 少量読み取りと全体読み取り

```sh
mise run probe -- /dev/rdisk8 --output artifacts/probe-20261020-230927
mise run rip -- /dev/rdisk8 --output artifacts/rip-20261020-231010
```

上の出力先は取得済みのため再利用できない。再実行時は新しい名前に変える。

| 検証 | 結果 |
| --- | --- |
| 少量読み取り | 各曲の先頭・中央・末尾付近、39セクターを2パス読み取り、全位置で一致 |
| 全体読み取り | 265,649セクターを2パス読み取り、全バイト一致 |
| 全体読み取りの単位 | 1要求16セクター、最後の要求は残りの1セクター |
| 音声読み取り要求数 | 33,208回、全件`read_ok`、I/Oエラー・再試行なし |
| TOCの変化 | 各パス終了時とも変化なし |
| 全体読み取り所要時間 | 約7分10秒、2パス合計 |
| 保存後の確認 | ファイルサイズと再計算したSHA-256がレポートと一致 |

音声イメージのSHA-256は、各パスと保存ファイルで同じだった。

```text
974dd6e640a3bdee382e62929119810bbf0df52bfcb15d2f3c39d742ccf7f6b9
```

`audio.bin`、INDEX 01中心の`disc.cue`、`toc.bin`、`toc.json`、
`reads.jsonl`、`report.json`を保存した。

## cddafsとのサンプル比較

cddafsで公開された全13曲の`.aiff`を調べた。
ファイルはAIFF-Cで、COMMの圧縮形式は`sowt`。
44.1 kHz・16-bit・2チャンネルのlittle-endian PCMだった。
各曲ともSSNDを解析して求めたPCM開始位置はファイル先頭から2352バイトで、
PCM長はTOCの曲区間から計算した長さと一致した。

ヘッダーを除いた各曲のPCMについて、先頭・中央・末尾付近の合計39セクターを比較した。
すべての位置で、cddafs・最初のprobe・保存イメージのバイト列が一致した。
比較スクリプトは標準ライブラリのみを使用し、固定長のヘッダー除去ではなく
FORM・COMM・SSNDチャンクから位置と形式を調べた。

この比較はサンプル位置のみ。全曲PCMの全バイト比較ではない。
cddafsも同じドライブとOSを使うので、独立したセキュアリッピングとの照合でもない。
